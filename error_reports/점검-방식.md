# 오류 점검 방식 (11/20 개정)

## 목표

**명세가 실제와 맞는지 API 하나하나 확인하고, 그 결과로 설명서를 보정합니다.** Discord 제보는 그 과정에서 나오는 부산물입니다.

최종 프로젝트(MCP 로 AI 가 백테스트·주문)에서는 명세를 AI 설명서로 넣습니다. 명세가 실제와 다르면 AI 가 틀린 필드·형식으로 호출하므로, **문서 오류도 호출 오류만큼 중요하게** 봅니다.

## 섹터마다 하는 일: 「명세대로 보내면 명세대로 오는가」

| 확인 | 방법 |
| --- | --- |
| 응답 구조 | 필드 이름·개수, 배열/객체, 값 타입(문자열/숫자), 0건일 때 모양이 명세 표와 같은지 |
| 필수 필드 | 필수(Y) 필드를 하나씩 빼고 보내면 거절되는지 (`ETR023`·`ETR001`), 선택(N) 필드를 빼면 기본값대로 동작하는지 |
| 값·코드 | 설명에 적힌 코드 값·상한이 실제로 맞는지, 범위 밖 값을 넣으면 오류가 나는지 |
| 연속 조회 | `nxt_key` 흐름과 마지막 페이지 판단이 명세대로인지 |
| 헤더·형식 | Content-Type·Authorization 이 명세대로 필요한지 |
| 문서 자체 | 웹·엑셀 차이, 설명과 필수 칸 모순, 정의 없는 필드, 샘플과 표 불일치 (0번 결과 재사용) |

## 찾은 것은 두 군데에 넣는다

1. **설명서 「실제 동작」 칸** (팀 로컬 NH API 설명서의 `corrections.json`): **무조건** 넣습니다. 다른 팀이 이미 제보했거나 운영진이 「정상」이라고 답한 것도 AI 가 알아야 하므로 넣습니다. 근거(운영 답변 / 실측 날짜 / 명세 모순)를 꼭 붙입니다.
2. **제보**: 아래 조건을 모두 만족할 때만.
   - Discord `#오류-문의` 에 같은 제보가 없음 (채널 검색, 팀 로컬 정리본과 대조)
   - 모의 환경 특성(24시간 체결, 2022년 이전 데이터, 불안정)이나 사용법 문제가 아님 (지금까지 운영진 판정 사례 기준)
   - 웹 가이드와 최신 엑셀을 둘 다 확인함
   - 근거(로그, 화면, 대조 결과)가 있음

**단순 표기 문제**(오타, 설명 잘림)는 버리지 않고 섹터마다 모아 한 건으로 묶습니다.

## 제보는 저장소에 먼저 정리하고 Discord 에는 나눠서

한 번에 여러 건을 올리면 채널이 도배되므로:

1. 제보문을 해당 섹터 폴더(`0-명세대조/` 등)에 한 건당 파일 하나로 씁니다 (`R01-….md`, 운영진 공지 양식 + 대조군·재현 횟수·가이드 링크).
2. 섹터 폴더에 제보문·로그(`logs/`)·재현 스크립트를 같이 둡니다 (다른 팀도 저장소 링크를 근거로 붙임).
3. Discord 에는 **하루 1\~2건씩**, 중요도 순서로 올리고 본문에 저장소 링크를 답니다.
4. 올린 날짜와 운영진 판정은 [README.md](README.md) 표에 기록합니다.

## 지킬 것

- **모의 서버에서만** 호출합니다. 조회 API 를 먼저 합니다.
- **주문·정정·취소**처럼 모의계좌에 실제로 주문이 들어가는 호출은 할 때마다 따로 확인받습니다.
- **실시간**은 재접속을 최소화합니다 (NH 11/04 경고). 연결을 끊을 수 있는 시험은 미리 확인받습니다.
- 요청 제한을 지킵니다 (팀 `nh_client.py` 의 속도 제한 사용).
- 스크립트는 섹터 폴더에, 로그는 그 아래 `logs/` 에 둡니다. 토큰·키·계좌번호는 지웁니다.
